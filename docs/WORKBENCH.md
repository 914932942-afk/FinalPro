# 工作台与 HTTP 演示服务

## 目的与范围

页面把已有的 Agent 流程变成可交互的业务演示：员工提出问题、补齐信息，经理确认具体审批计划，处理人核查证据并反馈。浏览器没有身份决策、审批授权或模型执行权限，所有规则仍在后端。

前端是 FastAPI 同源提供的静态 HTML/CSS/JS，无需 npm、前端路由框架或额外登录后端。选择这个方案是为了让状态、证据和人工接管可见；不为了展示前端技术而引入额外服务。

## 启动

已有虚拟环境与 `.env` 的机器双击根目录 `run_workbench.bat`，或在项目目录执行：

```powershell
.\.venv\Scripts\python.exe -m app.workbench
```

- 页面：`http://127.0.0.1:8080`，接口文档：`/docs`。
- 独立下游：`http://127.0.0.1:8091`，持久化到 `data/demo_service.db`。
- 首次运行若缺少身份配置，初始化四个本地身份。为缺少密码的身份生成独立初始密码，已有密码不覆盖。
- 页面使用账号密码登录；本机 `data/auth.accounts.txt` 交付初始密码，alice/bob 为员工、manager 为经理、admin 为管理员。服务端读取 `auth.json` 的密码哈希、身份和部门，不接受前端提交角色。
- 页面使用 HttpOnly、SameSite=Strict 会话 Cookie，最长 8 小时，刷新可恢复，退出后服务端撤销。密码与会话凭据不写入 localStorage/sessionStorage。会话数据库只存 Cookie 的摘要；HTTPS 下 Cookie 带 Secure。
- Cookie 认证写操作要求同源来源及 CSRF 校验，登录有频率限制。CLI 的 API Key 继续保存在 `data/auth.keys.json`，网页登录不使用它。
- 服务间使用另一个随机 Key，保存在 `data/demo_service.key`，不是用户 Key。
- 启动器用子进程环境变量启用 `http_incidents`，不修改用户 `.env`；Ctrl+C 停止它启动的两个子进程。
- 自定义端口：`python -m app.workbench --port 8090 --service-port 8091`。端口已占用会停止启动，不杀死其他进程。

直接执行 `python -m app.api` 仍可打开页面，使用 `.env` 中的动作模式。默认 `simulated` 仅在进程内模拟。已有旧身份配置时先执行 `python -m app.auth init-passwords`。账号文件中禁用用户或更换密码哈希会在后续请求中生效，旧会话被拒绝；该初始化命令不会重置已有密码。API 仍可供 CLI、测试及其他客户端使用。

网页登录接口为 `POST /auth/login`、`GET /auth/session`、`POST /auth/logout`。前端同源请求带 `X-Portal-Request: 1`，登录/恢复返回身份及 CSRF Token，后续写操作通过 `X-CSRF-Token` 提交。Cookie 由浏览器保存，响应正文不返回登录密码、API Key 或会话 Cookie。初始账号交付文件、认证文件和会话库均不进入版本库。

## 面试演示顺序

1. 用 alice 的账号、密码登录，提交“系统打不开”。按追问补充“ERP 以前正常，现在打开报错超时”。观察同一工单从补充信息到受理的变化。
2. 开启真实模型与调查时，事件先登记，调查在后续执行。员工查看处理进度和待办；经理、管理员在独立的“审批与处理”入口查看排查摘要和依据。诊断假设不能等同于已验证根因或故障修复。
3. 提交“申请报表数据库只读权限”。确认模型提出的具体计划，再切换 manager 审批。申请人不能审批自己的申请。ERP/VPN 只支持普通使用权限，不能申请报表库的只读权限类型。
4. manager 进入“审批与处理”，从“待认领”队列认领工单，再核查证据、请求用户补充、转派或提交处理结果。没有调查报告也可人工处理。建议采纳与问题是否解决分开记录；未解决仍保留处理待办，确认恢复才结束工单。演示输入的反馈不自动成为实验中的真实人工评审证据。
5. 用 bob 的账号、密码登录，不能看到 alice 的工单。手工调用接口也仍受后端权限限制。

## 故障工单的持续处理

登记成功后，故障先排队调查；无法调查或调查结束后进入“待支持核查”，不再以关闭工单代表已解决。支持人员先认领，工单进入“支持处理中”。申请人始终只在自己的工单中查看进度、处理团队及当前负责人，补充信息不改变已授权的账号、资源或动作。

调查缺少发生时间、具体表现、复现步骤或此前使用情况时，可向申请人提出受控问题。内部日志缺失、数据源不可用等问题交给支持人员核查，不要求普通用户提供内部配置。申请人补充后沿用原登记回执启动新一轮调查，旧观察与报告留在调查历史中；默认最多 3 轮调查、2 次自动追问，达到预算后由支持人员继续跟进。即使未收到自动追问，申请人也能为尚未结束的故障补充信息。

支持入口提供“待认领”“我负责的”“已超期”队列。认领与转派校验当前版本，避免多人同时抢占；申请人不能认领自己的申请，转派目标必须启用且具备工单对应支持组权限。只有当前处理人可以请求补充或提交结果，管理员可填写原因后接管，人员变化保留历史。处理人停用、降权或退出支持组后，巡检解除认领并回到可分配队列，旧页面版本随之失效。

### 部门审批与支持组权限

`auth.json` 由本机管理员维护，支持 `employee`、`support`、`manager`、`admin` 四种角色。`support_groups` 使用稳定标识：`network`（VPN）、`applications`（ERP）、`data`（报表数据库）、`service_desk`（本人账号及尚未确认系统的请求）。`support` 和配置了支持组的 `manager` 可跨部门处理对应服务；普通部门经理仅查看、审批本部门的权限申请，不因此取得故障日志或处理权限。支持组成员身份本身不授予业务审批权；申请人不能审批或处理自己的申请。

默认四个演示账号保持不变，`manager` 兼任四个支持组，便于本地复现。旧身份文件仅为缺少 `support_groups` 的演示 `manager` 补齐组，其他旧账号补为空组；已明确配置的空组不被覆盖，Key、密码哈希和归属保留。示例支持账号的配置结构（须由初始化或密码哈希工具生成有效凭据，以下省略凭据字段）：

```json
{"user_id": "network_support", "role": "support", "department": "IT", "support_groups": ["network"], "enabled": true}
```

认证、会话、审批和新工具调用均读取当前身份配置；停用即时拒绝后续请求，角色、部门、支持组或密码变化会使旧浏览器会话失效。审批默认有效 24 小时（`AGENT_APPROVAL_TTL_HOURS`），绑定申请人身份和具体执行计划；审批时及实际调用工具前再次检查启用状态、部门、审批人资格和有效期。失效及缺少身份绑定的历史未决审批转人工核查，不能继续授权；恢复执行同样受检查。已完成的回执只重放历史结果，不因账号后续停用再次调用下游。

`/portal/...`、旧 `/tickets/...`、审批接口和常规 CLI 采用一致的数据边界。申请人只收到业务状态、本人申请与需补充事项；`/state` 对申请人同样返回经过筛选的视图。诊断报告、模型轨迹、检索文档、工具账本和内部快照仅供具有对应支持组权限的处理人员及管理员查看，部门审批人仅得到审批业务信息。

### 刷新、重试与重复提交

页面在发出请求前，把本次提交编号和内容保存在当前标签页的 `sessionStorage`，按登录账号隔离。刷新并恢复登录后，会显示待确认内容，由用户点击“继续确认本次提交”，不会自动再次发起操作。确认收到工单后清除待提交内容；退出登录也清除当前账号的缓存。浏览器禁用存储或缓存损坏时不影响登录，当前页面仍保留重试信息，并提示先查看“我的工单”。缓存不保存密码、API Key 或会话凭据。

后端还独立检查业务重复：同一申请人、部门、标题、描述及影响程度相同的未结束工单，复用原工单并返回当前进展，即使客户端换了提交编号或未提供幂等键也不会再次建单。仅折叠文本中的格式空白；不会让模型自动合并语义相似的问题，也不会改写原描述或影响程度。用户会看到已打开原工单的提示，可以继续补充、跟进或验证。

已撤销、已拒绝、已归档、已验证解决以及审批已失效的申请可用新的提交编号重新申请。密码重置或授权已经自动成功时，默认在完成后 600 秒内复用原回执，避免响应丢失导致再次执行；超过窗口可正常发起新申请。`AGENT_SUBMISSION_COMPLETED_WINDOW_SECONDS=0` 可关闭这段成功结果保护，但相同提交编号仍永久绑定原申请。故障已验证解决后再次报障可以生成新工单，也可以按原有规则重开原单。

`submission_cases` 保存业务指纹与工单映射，`submission_keys` 保存各次提交编号与原工单的绑定。首次映射、请求账本占位和初始快照在一个 SQLite 事务中提交；模型和下游调用在事务之外执行。并发标签页或独立进程提交相同内容只能有一个首次执行者。重复提交只读取已有状态，不自动恢复未知操作；支持人员仍通过现有恢复或人工核查流程处理。旧版工单仅增补索引元数据，原回执和快照保留。

原提交编号的已完成响应保持重放兼容；因业务重复或仍在处理而复用原工单时，创建接口返回 HTTP 200，并包含安全的 `submission` 提示（`reused`、`reason`、`ticket_id`）。新建仍返回 HTTP 201。同一编号更换内容返回 409，不会把它绑定到另一张工单。账号角色或部门变化后重新认证，用原编号确认时只读取原申请；新申请的身份与审批条件仍按当前配置验证。

处理期限按严重程度设置：critical 1 小时、high 4 小时、medium 24 小时、low 72 小时，采用连续计时。等待申请人补充时暂停，收到回复后顺延等待时长。每 30 秒检查超期，写入一次升级记录并在支持队列突出显示；当前提醒范围是站内队列，没有邮件、短信或外部值班平台集成。

支持人员认为已恢复时，故障进入 `awaiting_verification`；申请人实际验证后确认，才进入 `resolved`。`rejected` 表示人工拒绝处理，`archived` 表示结束受理但未确认解决。反馈为未解决或尚未确认时回到可处理状态。结果未知的下游写操作必须先核查并在人工处理时填写凭证，不能通过普通反馈、撤回或无凭证归档跳过。历史已结束记录不强制改成待验证；在有效期内仍可由申请人重新打开。

用户等待默认规则：补充信息 48 小时、站内提醒 24 小时；超时解除 SLA 暂停并回到支持待办，处理人可继续联系或归档。支持侧提交处理结果后，验证期 72 小时、站内提醒 24 小时；超时归档为未确认解决。结束后 7 天内允许原单重开，恢复跟进期限，保留原登记、报告版本及各次处理记录。用户也可在处理过程中明确报告已自行验证恢复，或撤回后续处理，已发生的登记不会被撤销或重放。归档、撤回、解决分别记录，不能混淆。

申请人入口为 `POST /portal/tickets/{id}/verify`，提交 `revision`、`verdict=confirmed/still_failing/recurred` 和 `note`（未恢复或复发时必填）。只有申请人可调用，版本过期或超过重开窗口会拒绝。HTTP 的 `/tickets/{id}/feedback`、`/tickets/{id}/resolve` 均要求页面读到的 `case_revision`；CLI 对应提供 `--case-revision`，申请人验证使用 `verify 工单ID --revision 版本 --verdict confirmed`。工单版本在报告交付、认领转派、补充、处理结果及验证等变化时递增，旧页面不能核查新报告。

业务期限配置为 `AGENT_CASE_USER_REPLY_HOURS`、`AGENT_CASE_USER_REMINDER_HOURS`、`AGENT_CASE_VERIFICATION_HOURS`、`AGENT_CASE_VERIFICATION_REMINDER_HOURS`、`AGENT_CASE_REOPEN_DAYS`。由工作台后台巡检执行，提醒仅进入站内动态，不包含邮件或短信集成。

新增同源入口如下；权限、状态和版本仍由服务端校验，Cookie 写请求继续要求 CSRF：

| 入口 | 作用 |
|---|---|
| `GET /portal/tickets?scope=support&queue=unassigned/mine/overdue` | 读取对应支持队列（queue 选择一个值） |
| `POST /portal/tickets/{id}/claim` | 携带 assignment revision 认领 |
| `POST /portal/tickets/{id}/transfer` | 携带 revision、目标 assignee 和 reason 转派 |
| `POST /portal/tickets/{id}/request-info` | 携带 assignment revision 和受控 field 请求补充 |
| `POST /portal/tickets/{id}/follow-up` | 申请人携带 case revision 和 answer 补充信息 |

CLI 同样提供 `claim`、`transfer`、`request-info`、`follow-up` 子命令及 `--revision` 参数，支持流程仍受同一服务层约束。

## 后台排查异常与超时

排查任务的排队时间、运行期限、执行代次、运行次数和失败原因保存到业务快照。默认最多 2 个后台工作线程、100 个等待任务；独立巡检每 5 秒检查，排队最长 120 秒、单次运行最长 90 秒。任务异常、超时或工作线程中断后，工单进入可认领的支持待办，用户无需一直等待“正在排查”。关停服务也不会无限等待卡住的后台调用。

支持人员认领后，可在异常提示中查看剩余次数并选择“重新排查”。入口为 `POST /portal/tickets/{id}/retry-investigation`，提交当前 `case_revision`；服务端检查当前负责人、工单状态、未知操作以及持久化预算。默认每轮最多运行 3 次，达到上限保留人工处理入口并记录升级，重启不能清零次数。CLI 可用 `retry-investigation 工单ID --revision 版本` 排队，再执行 `investigate 工单ID`；网页后台启用时会自动消费已排队任务。

重新排查继续使用同一故障事件和已有只读证据，工具、模型计数不会清零；新运行的时间窗口由显式重试开启。原始登记不重放。附件写入超时仍按结果未知处理，只能核查回执并持凭证结案，不能通过重新排查绕过。

工作线程在只读调查期间不占用整张工单的处理锁。每次保存检查任务代次和期限，超时、人工结案或新代次开始后，旧任务不得覆盖新状态或发起新的附件写入；已经在途的未知写入仍需核查回执。Python 线程内的底层调用不能被安全强杀；该机制撤销旧任务的回写资格，使用有限的后台线程控制资源占用，网络调用同时保留自己的超时。

配置项为 `AGENT_DIAGNOSIS_WORKER_TIMEOUT`、`AGENT_DIAGNOSIS_QUEUE_TIMEOUT`、`AGENT_DIAGNOSIS_WORKER_MAX_RUNS`、`AGENT_DIAGNOSIS_WORKER_POLL` 和 `AGENT_DIAGNOSIS_WORKERS`。用户门户只显示处理状态和下一步，执行代次、预算与技术异常不会作为原始日志展示给申请人。

## HTTP 契约与结果未知

Agent 的 `IncidentHTTPAdapter` 使用独立 HTTP 服务，并复用原有操作账本：

| 请求 | 作用 | 约束 |
|---|---|---|
| `POST /incidents` | 登记故障事件 | Bearer 服务凭据、固定幂等键、结构化回执 |
| `POST /attachments` | 附加调查证据 | 独立幂等键、必须先存在事件 |
| `GET /operations/{key}` | 只读查询操作回执 | 不重复写入、不自动把 Agent 账本改为成功 |
| `GET /ready` | 检查服务认证和数据库读取 | 无业务写入 |

独立服务把业务对象与幂等回执放在同一个 SQLite 事务中。同键同内容返回已有回执，同键不同内容拒绝；重启后回执仍可查询。

`/attachments` 的 `version` 对应调查轮次，主键为工单加版本；同一工单允许多份报告，原版本禁止覆盖。缺少 `version` 的旧请求仍按版本 1 接收，旧回执的内容指纹保留，迁移和重启不会重复写入旧附件。

新事件的 `/incidents` 请求保留原始 `title`、`description`，并携带 `registration_context`：`version=1`、`effective_description`（登记时有效的故障描述，明确更正会替换旧理解）、`clarifications`（登记前各轮用户补充）、`input_digest` 和 `plan_digest`。该快照在首次调用前保存，与验证过的用户证据和执行计划绑定；恢复时校验一致性，工具账本对完整出站数据计算指纹。不会把助手提示、模型轨迹或内部调用数据当作用户补充发送。

登记后的调查补充继续保存在原工单和调查历史中，初始登记快照保持原样。旧事件及没有快照的旧回执不自动补写，旧请求省略新增字段，继续使用原幂等契约。这次改动完善的是本地演示服务的数据传递，未接入真实企业系统。

网络超时不等于下游未执行。写入成功而响应丢失时，Agent 保持待核查，不自动重试写操作；经理可从页面读取账本与下游回执，再按实际核查结果人工结案。附件失败不删除已登记事件，也不重新登记。调用方和服务之间不具备分布式事务，不声称全链路 exactly-once。

页面建单使用固定请求标识；受理响应丢失时锁定原内容，重试复用原标识。标识仅在当前页面内存中保存，刷新或切换身份后不保留，因此结果未知时应先查看工单列表再决定后续处理。敏感状态变更不自动重试。

HTTP 连接和失败处理是真实的，但下游是本地独立演示系统，日志与业务对象仍是模拟数据。密码重置、权限授予仍使用明确标注的本地模拟适配器。将来接企业接口还需要按实际契约适配认证、字段、幂等及结果查询，不能只替换 URL 就宣称接入完成。

## 预检与验证证据
